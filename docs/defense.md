## Почему не один агент

Коротко: **один свободный агент на слабой модели теряет обязательные шаги, тратит токены на маршрутизацию и не укладывается в лимит. Жёсткий конвейер физически не даёт пропустить Verification и Approval** ([ADR 0001](adr/0001-fixed-agent-pipeline.md)).

1. **Обязательные шаги нельзя пропустить.** Порядок этапов задан рёбрами графа LangGraph, Orchestrator — условные переходы в коде, а не LLM. Модель не может «решить», что Fix и так хороший, и перескочить через сборку, Critic или Approval человека. У одного агента с инструментом `create_pr` такой гарантии нет.
2. **Токены идут на работу, а не на маршрутизацию.** Супервизор-LLM тратит отдельный запрос на каждое «кто следующий». Разработка шла на бесплатном Groq (8 000 токенов в минуту), там каждый запрос на счету.
3. **Контекст этапа маленький.** Между этапами передаются только итоги (`analysis_summary`, Plan, diff, хвост лога), а не переписка модели с инструментами. Иначе к Coder доходят сотни килобайт поиска Analyst, и запрос не влезает в лимит.
4. **У каждого этапа свой набор прав.** Analyst и Planner только ищут и читают, Coder ещё и пишет, у Critic инструментов нет совсем. Git, Docker и GitHub вызывает граф: модель не может сделать push, оставить комментарий или запустить произвольную команду.
5. **Перепланирование ограничено.** Неудачный Fix возвращается к Planner с `critic_notes`, но не больше 3 попыток, потом — честный итог «агент сдался». Один агент может крутиться бесконечно.

Цена решения: агент не умеет отступать от сценария. Например, Analyst не может сам решить «сначала починю красный Baseline». Вместо этого он выносит Verdict «Заблокировано» и называет связанное issue, а порядок выбирает человек.

Паттерны из ТЗ: **ReAct** — внутри Analyst, Planner, Coder; **Plan-and-Execute** — Planner пишет Plan, Coder исполняет; **Reflexion** — петля Critic → Planner.

## Как проверяется код

Коротко: **Fix проверяют две сборки `docker build` с тестами и Critic, а потом человек. «Исправлено» мы утверждаем только для Reproduced Fix — когда тест из Fix падает на исходном коде и проходит с Fix** ([ADR 0002](adr/0002-verification-via-docker-build.md)).

1. **Механика — одна команда.** Target Repository обязан иметь `Dockerfile`, который компилирует проект и прогоняет тесты (`mvn package` без `-DskipTests`). «Образ собрался» = «скомпилировалось и тесты прошли». Агенту безразличен язык проекта: у Executor один сигнал — код возврата и хвост лога. Таймаут — 5 минут.
2. **Baseline до любых правок.** Граф собирает исходный код. Если он красный, Analyst видит упавшие тесты и решает, связаны ли они с Bug Report. Если не связаны — Verdict «Заблокировано»: любой Fix всё равно не пройдёт проверку.
3. **Сборка B — весь Fix.** Должна пройти. Не прошла — Fix возвращается к Planner с логом.
4. **Сборка A — только тесты из Fix на исходном коде.** Executor берёт из Fix файлы под `src/test/**` и собирает их без исправления. Если упал тест, который был зелёным в Baseline, — это **Reproduced Fix**: тест ловит именно этот баг. Если A прошла, не дошла до тестов или теста нет — **Unreproduced Fix**, и это прямо написано в Fix PR: «известно лишь, что Fix собирается и не ломает существующие тесты».
5. **Critic (Reflexion).** Отдельный вызов модели без инструментов видит Bug Report, Plan, diff и результат сборки. Проверяет, устраняет ли diff именно описанный симптом и не задевает ли лишнего. Может вернуть Fix в Planner с замечаниями.
6. **Человек.** Каждый Plan проходит Plan Approval, итоговый diff — Fix Approval. Агент только создаёт Fix PR, мержит человек.

Что это не гарантирует: Unreproduced Fix может «собраться и выглядеть логично», но не исправлять баг. Поэтому он помечен честно, а не выдан за проверенный.

### Что показать в трейсах

- **Human-in-the-Loop с доработкой.** #1, второй заход: на Plan Approval человек ответил «Доработка не должна быть на уровне БД», и Planner перенёс исправление из JPQL-запроса в `BookingServiceImpl`. #3: комментарий «Нам надо как-то идентифицировать минимально платежи» превратил «не логировать карту» в «логировать маску `****1111`».
- **Петля Critic.** #1, третий заход (Thread в LangSmith, Turn 3): `verification_passed = false`, `attempts = 2`, затем снова Plan Approval с причиной отказа.
- **Заблокировано.** #5: граф сам нашёл открытые issue, Analyst сопоставил упавший `bookingRightAfterConfirmedOneIsAllowed` с #1 по смыслу и назвал его в комментарии.

### Честно о слабых местах (видно в этих же трейсах)

- **Critic отклонил верный Fix из-за хвоста лога.** Замечание Critic: «код возврата 0 подтверждает только успешную сборку образа из кэша… в логе нет результатов тестов». У многостадийного Dockerfile последние 60 строк лога — это сборка runtime-образа, а отчёт Surefire остаётся выше. Петля сработала, но по ложной причине. Исправление — передавать Critic строку итогов тестов из лога, а не просто хвост.
- **Coder пишет в объяснение «тесты не запускал: нет инструмента».** Фраза попадает в Fix PR (#8, #9, #10), хотя Executor тесты запускал. Это нужно убрать из промпта Coder.
- **Ошибка сборки A не видна.** Если Git или Docker падают при сборке A, `build_reproduction` молча возвращает `None`, и Fix становится Unreproduced без объяснения.
- **Не закончены пункты задачи 07:** выбор модели Groq, промпт Critic о наблюдаемом симптоме, дубли в трейсе, отдельный трейс сценария 1 с выводом упавших тестов в качестве Bug Report.
