# Bug Investigator — спецификация

Термины — по `GLOSSARY.md`. Архитектурные решения — `docs/adr/0001-fixed-agent-pipeline.md`, `docs/adr/0002-verification-via-docker-build.md`.

## Цель и рамки

Агент получает Bug Report, находит причину в Target Repository, готовит Fix, проверяет его в Docker и после Approval человека создаёт Fix PR в GitHub. Срок — 2 дня, один разработчик.

**В скоупе:** граф LangGraph, петля самокритики, паузы Human-in-the-Loop, готовые инструменты, повторы при сбоях, UI на Chainlit, трейсинг в LangSmith, реальный Fix PR.

**Вне скоупа:** ревью чужих PR, webhook (Sentry / GitHub), мультитенантность и GitHub App, база данных для агента, история Investigation в UI, все «идеи для расширения» из ТЗ. Агент никогда не мержит PR.

## Вход

- Bug Report — описание неправильного поведения; стек-трейс желателен, но не обязателен.
- Два способа: текст в чате Chainlit или ссылка на issue из Target Repository. Из issue берутся заголовок и текст, комментарии не читаются.
- Target Repository и ветка (`main`) задаются только конфигом стенда.

## Граф

Порядок этапов жёсткий (ADR 0001). Orchestrator — условные переходы в коде.

```
Подготовка   (код)    клон --depth 1 во временную папку, новая ветка
Baseline     (код)    docker build исходного кода
Analyst      (ReAct)  Verdict + analysis_summary
  ├ Подтверждено        → Planner
  ├ Не баг              → пауза Approval → комментарий в issue → конец
  ├ Недостаточно данных → комментарий в issue → конец
  └ Заблокировано       → комментарий в issue (+ ссылка на связанное issue) → конец
Planner      (ReAct)  Plan: причина, Reproduction, изменение
Plan Approval         пауза
Coder        (ReAct)  Fix: правка кода и, если возможно, тест-Reproduction
Executor     (код)    сборка A (только тесты из Fix) и сборка B (весь Fix)
Critic       (LLM)    видит Bug Report, diff, лог; без инструментов
  └ не прошло → Planner с critic_notes, максимум 3 попытки → «агент сдался»
Fix Approval          пауза
Публикация   (код)    коммит, push, Fix PR в main
```

«Доработать» на любой паузе возвращает на предыдущий этап с комментарием человека: Plan Approval → Planner, Fix Approval → Planner, «Не баг» → Analyst.

### Baseline и «Заблокировано»

Если Baseline красный, Analyst получает имена упавших тестов вместе с Bug Report и решает, связаны ли они. Если связаны, работа идёт как обычно. Если не связаны, выносится Verdict «Заблокировано». Перед этим граф (не модель) ищет открытые issue в Target Repository по именам упавших тестов и исключений и передаёт Analyst до 5 заголовков. Analyst указывает в комментарии связанное issue, если нашёл.

### Verification

Механика — `docker build` с тестовой стадией (ADR 0002), таймаут 5 минут.

- **Сборка A:** только новые и изменённые файлы под `src/test/**` из Fix. Должна упасть.
- **Сборка B:** весь Fix. Должна пройти.
- A упала и B прошла — Reproduced Fix. B прошла, а A прошла или теста нет — Unreproduced Fix. B упала — к Critic как провал.
- Затем Critic проверяет, объясняет ли diff Bug Report и не задевает ли лишнего; может вернуть Fix Planner'у.

Если не хватит времени, сборку A убираем первой: тогда все Fix помечаются Unreproduced.

## Инструменты модели

| Инструмент | Источник | Analyst | Planner | Coder | Critic |
| --- | --- | --- | --- | --- | --- |
| `grep` (`definitions_only`), `find_files` | `fff-search` (Python SDK) | ✓ | ✓ | ✓ | |
| `list_directory`, `read_file` | `FileManagementToolkit`, `root_dir` = рабочая копия | ✓ | ✓ | ✓ | |
| `write_file` | `FileManagementToolkit` | | | ✓ | |

Git, Docker и GitHub (чтение issue, поиск issue, комментарии, Fix PR) вызывает граф. Собственный инструмент правки заменой фрагмента пишем только если `write_file` на прогонах теряет куски файлов.

## State

```
bug_report        текст, источник, номер issue
workdir, branch
baseline          код возврата + упавшие тесты
verdict, analysis_summary
plan, plan_approval
fix_diff, fix_explanation, reproduced
build_result      код возврата + хвост лога
critic_notes, attempts
fix_approval
outcome           PR создан / отклонено / агент сдался / не баг / мало данных / заблокировано
pr_url
```

Между этапами передаются только итоги, переписка модели с инструментами дальше не идёт. Секреты в state не кладём никогда: он уходит в трейсы LangSmith.

## Паузы и UI

- `interrupt` LangGraph + `InMemorySaver` (пауза живёт, пока запущен процесс).
- Chainlit: один шаг на узел графа со статусом («Analyst ищет проблемное место…»).
- Каждая пауза — сообщение с содержимым (Plan, diff + объяснение + Reproduced/Unreproduced, обоснование «не баг») и кнопки «Одобрить», «Отклонить», «Доработать». «Доработать» просит комментарий следующим сообщением.

## Комментарии в issue

Только если Bug Report пришёл из issue:
- «Не баг» — после Approval;
- «Недостаточно данных» — сразу, с перечнем чего не хватает;
- «Заблокировано» — сразу, с упавшими тестами и ссылкой на связанное issue.

Связь Fix PR с issue — `Fixes #N` в описании.

## Fix PR

Ветка `bug-investigator/<номер issue или короткий хэш>`, при конфликте имени — суффикс. В описании: Bug Report или `Fixes #N`, найденная причина, описание изменения, Reproduced/Unreproduced с результатами сборок, пометка «создано агентом». Собирается шаблоном, без вызова модели.

## Лимиты и сбои

- Не больше 15 вызовов инструментов на заход агента (`recursion_limit`).
- Не больше 3 попыток петли Planner → Critic.
- Временные сбои (таймаут, rate limit, сеть) — автоматические повторы с растущей паузой, модель о них не знает.
- Ошибки по существу (файл не найден, пустой поиск) — текстом в результат инструмента, модель меняет план.
- Повторы исчерпаны — финал «агент сдался» с объяснением.
- Чтение и поиск ограничены по объёму ответа: лимит Groq около 8 000 токенов в минуту.

## Модели и наблюдаемость

- Провайдер и модель — в конфиге. Разработка на Groq (бесплатный тариф), финальные прогоны и защита — на недорогой модели OpenAI (бюджет $5).
- Модель Groq с надёжным tool calling выбираем прогонами.
- LangSmith подключён с первого запуска графа.

## Стенд `resourceBooking`

- Java / Spring Boot, остаётся на Java. Тесты на H2 в памяти, Dockerfile с `mvn package` без `-DskipTests`, зависимости отдельным слоем.
- `main` чистый и зелёный, на нём тег `clean`.
- Наборы багов — ветки от `main`, по 3 бага в каждой: явный (валит существующие тесты), тихий с возможным тестом, тихий без возможного теста (например, в `FakePaymentServiceImpl`). 1–2 набора для своих прогонов, 1–2 — для проверяющего.
- Сценарий: человек вливает набор в `main`, запускает агента; агент сам направит начать с явного бага через Verdict «Заблокировано».
- Проверяющий получает список наборов с одной строкой «что примерно сломано» и пишет issue своими словами.
- Сброс (вручную, не агентом): `git reset --hard clean` и `git push --force origin main`, открытые Fix PR закрываются в GitHub.

## Сценарии защиты

1. Явный баг: Bug Report — вывод упавших тестов, Fix PR, человек мержит.
2. Тихий баг с тестом: Reproduced Fix.
3. Тихий баг без теста: Unreproduced Fix с честной пометкой.
4. Тихий баг до явного: Verdict «Заблокировано».
5. Петля Critic — показываем записанный трейс LangSmith, если вживую не воспроизвелась.
