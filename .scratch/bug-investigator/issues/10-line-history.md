# 10 — История строк: инструмент `line_history`

Status: needs-triage
Blocked by: 09

Многие баги — регрессии: строку недавно поменяли, и поведение сломалось. Сейчас модель видит только текущее состояние кода; git вызывает граф, а сама модель — нет. Инструмент, показывающий, как менялся диапазон строк, позволит Analyst быстрее найти причину, а Planner — обосновать Plan («до коммита X здесь было `> 0`»).

## Готово, когда

- [ ] Рабочая копия клонируется с историей: `git clone --filter=blob:none` вместо `--depth 1` (`workspace.py`); время клона на стенде сопоставимо с текущим
- [ ] Инструмент `line_history(path, start_line, end_line, max_commits=3)` в `tools.py`: `git log -L start,end:path -n max_commits --format="%h %as %s"` по `HEAD`, вывод через `_limited`
- [ ] Понятные ответы вместо исключений: файла нет в истории, диапазон вне файла, у строк один коммит («строки не менялись с <hash> <дата>»)
- [ ] Инструмент есть у Analyst и Planner, нет у Coder и Critic; строка добавлена в таблицу «Инструменты модели» в `spec.md`
- [ ] Промпты Analyst и Planner: звать `line_history` точечно, на уже найденном подозрительном методе, а не на целом файле
- [ ] Тест в `tests/test_tools.py` на временном репозитории из двух коммитов: второй меняет одну строку, инструмент показывает оба коммита и diff строки
- [ ] Проверено, что стенд не подсказывает ответ (см. ниже)

## Риск: стенд подсказывает ответ

Если баги в `bugset-*` (`angryelizar/resourceBooking`) внесены отдельными коммитами с говорящими сообщениями («inject bug: overlap `>=`»), `line_history` сразу укажет на баг, и прогоны будут мерить чтение сообщений коммитов, а не поиск. Перед подключением посмотреть `git log` веток наборов. Если сообщения выдают баг — спрятать: влить в правдоподобные коммиты-фичи или переписать сообщения, чтобы история выглядела как у живого проекта, где регрессия приехала вместе с фичей. Набор `bugset-3`/`bugset-4` проверяющего — обязательно.

## Заметки

- Бюджет Groq (09): вывод `log -L` растёт быстро, поэтому `max_commits` маленький по умолчанию и с верхней границей (например, 5). Поэтому задача и блокируется 09: сначала Investigation должна укладываться в лимит без нового инструмента.
- Номера строк — по `HEAD`. Analyst и Planner работают до правок Coder, так что рабочая копия совпадает с `HEAD`; если это изменится, инструмент должен предупреждать о незакоммиченных правках в файле.
- `git blame -L` слабее: показывает лишь последний коммит на строку без прошлой версии. Pickaxe (`git log -S <строка>`) — возможное продолжение, если `line_history` окажется полезным на прогонах.
- С `--filter=blob:none` старые версии файлов докачиваются по сети при первом `log -L`; на прогонах проверить задержку.
